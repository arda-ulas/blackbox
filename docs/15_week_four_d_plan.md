## 1. Thesis

W4-D migrates Blackbox from the legacy **string-smuggled** transcript encoding to a **structured, provider-neutral** transcript, so that tool-call correlation lives in **cassette data** instead of **adapter memory**.

Today the provider correlation needed to continue a run lives only in `#pendingToolCalls` on a single live `AnthropicModelClient` instance (`src/agent/anthropicModelClient.ts`). The transcript itself carries only:

- assistant turn: `content: "[tool_call:<toolName>]"` (a label — no id, no input)
- user turn: `content: JSON.stringify(toolResult)` (a bare value — no toolName, no id)

A fresh adapter reading a cassette therefore cannot rebuild a correlated request, which is exactly why real-provider fork/continue is deferred. After migration, every tool call carries a **deterministic, provider-neutral `toolCallId`** stored in *both* the assistant `tool_use` part and the user `tool_result` part. Reconstruction becomes a pure function of cassette content — no adapter memory required.

**What W4-D proves:** the record → replay → fork → mutate → diff loop holds on a structured, provider-neutral transcript, using the fake model and a mocked Anthropic client.

**What W4-D does NOT prove:** that a real Anthropic API accepts a Blackbox `toolCallId` as a provider `tool_use.id`. That verification is deferred to **W4-E** (Context7 + installed types + a live proof). W4-D must not claim it. See §3.3 and §9.

## 3. Proposed Schema

### 3.1 `MessagePart` (error-capable, provider-neutral)

Add to `src/agent/modelClient.ts`:

```ts
export type MessagePart =
  | { type: "text";        text: string }
  | { type: "tool_use";    toolCallId: string; toolName: string; toolInput: JsonValue }
  | { type: "tool_result"; toolCallId: string; toolName: string; result: JsonValue }
  | { type: "tool_result"; toolCallId: string; toolName: string; error: string };

export interface Message {
  role: "user" | "assistant";
  content: string | MessagePart[];   // plain-string text shorthand still allowed
}
```

- Plain user/assistant text stays `content: "..."` — existing string-based prompts and tests keep compiling.
- A tool round becomes: assistant turn `content: [{ type:"tool_use", toolCallId, toolName, toolInput }]`, then user turn `content: [{ type:"tool_result", toolCallId, toolName, result }]` (or the `error` variant on failure).
- **Role-aware typing** (e.g. `tool_use` only on assistant turns, `tool_result` only on user turns) is **preferred if it does not create excess churn**, but is **not required** for W4-D. Runtime construction already respects these roles.

`ModelOutput` is **unchanged** (`{ type:"tool_call", toolName, toolInput }`). The agent loop assigns `toolCallId` when it records, so the adapter response contract has zero blast radius.

### 3.2 `toolCallId` — the neutral correlation key

- **Generated by the agent loop**, deterministically, from run-local position: format `` `call-${n}` `` starting at `n = 0` (`call-0`, `call-1`, …). Must be a pure function of position so hashes are reproducible and fork prefixes stay identical.
- **Never** the provider's `tool_use_id`. The provider id is never persisted.
- **Fork-continuation sequencing (Codex correction #2):** when `runAgentLoop` starts from `initialMessages`, it must **seed the next tool-call index** from the structured messages it was handed (count existing `tool_use` parts) **or accept an explicit starting index**. Otherwise a continued run re-issues `call-0` and collides with the parent prefix. This is a required behavior with dedicated tests (§7).

### 3.3 Stored vs. not stored

| Field | Stored? | Why |
|---|---|---|
| `toolCallId` (neutral) | ✅ | Deterministic correlation; enables reconstruction |
| `toolName` | ✅ | Replay summary + re-dispatch |
| `toolInput` | ✅ | Recorded request content |
| `result` / `error` | ✅ | The cassette payload being replayed |
| provider `tool_use_id` / correlation id | ❌ | Provider-native — violates neutrality invariant; unnecessary |
| provider usage / message id / raw content array | ❌ | Provider-native — must never enter payloads |

**Load-bearing assumption, explicitly deferred:** on a real continuation, an adapter would synthesize a provider request from the neutral transcript (e.g. use `toolCallId` as the Anthropic block id). W4-D proves only that the adapter can **emit a self-consistent provider-neutral → provider-shaped request from cassette data with no pending state**, verified against a **mocked** client. Whether a live Anthropic API accepts a synthetic `tool_use.id` is a **W4-E** question, to be verified via Context7 + installed types + a live proof. W4-D docs and tests must not assert live acceptance.

## 4. Trace Payload Changes

- `tool_call` step payload: `{ toolCallId, toolName, toolInput }`
- `tool_result` step payload: `{ toolCallId, toolName, result }` — or the failure variant `{ toolCallId, toolName, error }`
- `model_input` step payload: `messages` now contains structured `MessagePart[]` where tool rounds occur
- No provider-native IDs in any payload.

`hash.ts` is **unchanged** — it already canonicalizes arbitrary `JsonValue` with sorted keys. The only requirement is that `toolCallId` be deterministic; if it were random, prefix identity would break. `validateTrace` and `replayTrace` remain schema-agnostic.

---

## 5. Migration Strategy

- **W4-D1: no schema bump.** Types and helpers only; still writing legacy payloads. Do **not** create v2 cassettes with v1 transcript semantics.
- **W4-D2: atomic bump.** Bump `CURRENT_TRACE_VERSION` 1 → 2 **in the same slice** that starts emitting structured transcript/payloads. Version and semantics change together.
- **Reject v1.** `loadTrace` already gates on version (`CassetteReplay.ts`); v1 cassettes get a clear message: *"cassette version 1 is unreadable by this build (schema v2); re-record with `npm run cli -- record`."*
- **No migration shim.** `traces/` is git-ignored and regenerated by `record`; there is no cassette corpus to preserve. A v1 → v2 migrator is an explicit non-goal.

## 7. Tests (all fake or mocked — no key required)

- v1 cassettes rejected with a clear re-record message.
- Structured `tool_use`/`tool_result` parts carry **matching** `toolCallId`.
- Multiple tool calls in one run produce `call-0`, `call-1`, … in order.
- **Fork continuation seeds the next id correctly and does not reuse `call-0`** (seed-from-`initialMessages` or explicit start index).
- Unknown-tool failure records `toolCallId` on the `error` payload variant.
- Fork with no mutation preserves prefix hashes (canonical-hash-identical prefix).
- Tool-result mutation **preserves `toolCallId`** and updates the continued model input; correct first divergence in `diffTraces`.
- Stale `model_input`-between-mutation guard remains tested (kept, not relaxed).
- A **fresh** `AnthropicModelClient` (no pending state, mocked client) translates cassette-derived structured messages into a self-consistent request, with `tool_use` id and `tool_result` correlation both equal to `toolCallId`.
- `replayTrace(trace)` remains `Trace`-only and offline — zero provider/tool calls.
- No provider-native field appears in any trace payload.
- Determinism: two records of the same scripted run → identical `toolCallId`s and identical step hashes.

`npm test -- --run` must stay green (count will rise; broad churn expected in tests that assert the old string encoding), with no live calls and nothing skipped.
